# Documentación del módulo Autenticación y Usuarios (Kiroku)

Integrante 1 (Maxi) · Pruebas de endpoints realizadas por el Integrante 2 (Steff) · Programación III · Repositorio `backend-grupo-LOTUS` · Rama `feature/visualizacion-maxi` · Octubre de 2026

## 1. Resumen

Este documento describe el módulo de **Autenticación, Seguridad y Usuarios** del proyecto Kiroku (Plataforma de Seguimiento y Reseñas de Anime): qué archivos lo componen, cómo funciona la seguridad con JWT y roles, qué endpoints expone y qué pruebas se hicieron sobre él.

El módulo permite registrar usuarios, iniciar sesión con contraseñas hasheadas, emitir tokens JWT y restringir operaciones según el rol (`STD` o `ADMIN`). Además provee los middlewares que usan los otros dos módulos del grupo (`authToken` y `authorize`).

**Resultado de las pruebas:** se ejecutaron 28 pruebas individuales de endpoints más un flujo integral con tres usuarios (dos comunes y un administrador). Todas dieron el código HTTP esperado. Los hallazgos menores y las recomendaciones están en la sección 8.

## 4. Decisiones de seguridad

1. **Contraseñas con bcrypt** (10 rondas de sal), aplicado en el hook `pre('save')` solo cuando el campo cambia. El campo `password` tiene `select: false` y `toJSON` lo elimina, de modo que no sale en ninguna respuesta.
2. **El rol no se puede elegir al registrarse.** El controlador fuerza `rol: 'STD'` aunque el cliente envíe otro valor.
3. **El perfil solo permite editar `nombre` y `avatar`.** Cualquier otro campo se rechaza con 400, lo que impide que un usuario se suba el rol.
4. **Mensaje único para credenciales inválidas.** El login responde 401 con el mismo mensaje tanto si el email no existe como si la contraseña es incorrecta, para no revelar qué cuentas existen.
5. **JWT con identidad y rol.** El token lleva el ID del usuario como `sub` y el rol como dato propio. Vence según `JWT_EXPIRY` (24 horas por defecto).
6. **`JWT_SECRET` exigente.** `env.js` rechaza secretos de menos de 32 caracteres o que contengan palabras típicas de ejemplo, y el servidor no arranca si no se cumple.
7. **Errores sin filtrar detalles internos.** Para errores 5xx el `errorHandler` devuelve un mensaje genérico y deja el detalle solo en la consola del servidor.
8. **Logger sin datos sensibles.** Registra la ruta sin el query string, para no guardar tokens que viajen en la URL.
9. **Las rutas administrativas combinan dos middlewares:** `authToken` (401 si falta o es inválido el token) y `authorize('ADMIN')` (403 si el rol no alcanza).

## 5. Endpoints

### Autenticación (`/api/auth`)

| Método | Ruta | Acceso | Descripción | Éxito | Errores |
| --- | --- | --- | --- | --- | --- |
| POST | `/api/auth/registro` | Público | Alta de usuario (rol `STD`) | 201 | 400 (datos inválidos), 409 (email repetido) |
| POST | `/api/auth/login` | Público | Valida credenciales y entrega el token | 200 | 400 (faltan datos), 401 (credenciales inválidas) |
| GET | `/api/auth/perfil` | Token | Datos del usuario de la sesión | 200 | 401, 404 |

### Usuarios (`/api/usuarios`)

| Método | Ruta | Acceso | Descripción | Éxito | Errores |
| --- | --- | --- | --- | --- | --- |
| GET | `/api/usuarios` | ADMIN | Lista todos los usuarios | 200 | 401, 403 |
| GET | `/api/usuarios/me` | Token | Perfil propio | 200 | 401, 404 |
| PUT | `/api/usuarios/me` | Token | Edita `nombre` y/o `avatar` | 200 | 400, 401 |
| GET | `/api/usuarios/:id` | ADMIN | Consulta un usuario | 200 | 400, 401, 403, 404 |
| DELETE | `/api/usuarios/:id` | ADMIN | Elimina un usuario | 204 | 400, 401, 403, 404 |

La ruta `/me` está declarada antes que `/:id`, que es el orden correcto para que Express no interprete `me` como un ID.

## 6. Metodología de pruebas

- **Herramienta:** Thunder Client contra el servidor local (`npm run dev`) conectado a MongoDB Atlas.
- **Autenticación en las pruebas:** pestaña *Auth → Bearer* con el token obtenido en el login. Se manejaron tres tipos de token: **STD** (usuario común), **ADMIN** y **sin token**.
- **Usuarios de prueba:** cuentas comunes con emails de prueba y una cuenta administradora.
- **Cómo se obtuvo el administrador:** como el proyecto no incluye un seed, se registró una cuenta normal y se cambió su rol a `ADMIN` con un script temporal ejecutado una sola vez y luego borrado. Después se volvió a iniciar sesión, porque el rol viaja dentro del token y uno anterior seguiría diciendo `STD`.
- **Criterio de aprobación:** el código de estado HTTP coincide con el esperado y las respuestas nunca incluyen el campo `password`.

## 8. Hallazgos y recomendaciones

Ninguno de estos puntos es un error que haya hecho fallar una prueba. Son mejoras o riesgos para tener presentes.

1. **Falta el script de seed.** El plan pide crear automáticamente un administrador y un usuario estándar si la base está vacía, pero el `package.json` solo tiene los scripts `start` y `dev`. Hoy, para probar las rutas de administración, hay que subir el rol a mano. Se recomienda agregar un `seed` (por ejemplo `npm run seed`). Como los tres integrantes comparten la misma base de Atlas, alcanza con crear el administrador una sola vez.
2. **El token de un usuario eliminado sigue siendo válido hasta que vence.** Es una propiedad normal de los JWT stateless: `authToken` no consulta la base. El perfil falla con 404 (paso 8), pero otros módulos que confíen en `req.user.id` para crear datos, como seguimientos o reseñas, deberían verificar que el usuario siga existiendo.
3. **El mensaje de error 409 menciona siempre el email.** El `errorHandler` traduce cualquier error de clave duplicada (código 11000) como "Ya existe un registro con ese email". Es correcto para usuarios, pero sería engañoso si otros módulos reutilizaran el manejador para duplicados de otra colección.
4. **Archivos de compatibilidad temporal.** `middlewares.js` y `usuariosController.js` solo re-exportan. Si ningún archivo los importa, conviene borrarlos antes de la entrega para no duplicar la estructura.
5. **Formato de respuestas de error.** Este módulo responde `{ mensaje }`, mientras que el catálogo de animes usa `{ error, mensaje, detalles }`. El frontend funciona con ambos porque comparten `mensaje`, pero conviene unificarlos.
6. **Nombres de archivos de rutas.** Este módulo usa `authRoutes.js` y `usuariosRoutes.js`, y los demás usan el patrón `animes.routes.js`. Es solo estético.
7. **Notas del entorno de instalación.** `npm install` avisa que `bcrypt` tiene un script de instalación sin aprobar y reporta 3 vulnerabilidades (2 altas y 1 crítica). El servidor arrancó y bcrypt funcionó sin problemas. Las vulnerabilidades conviene revisarlas entre los tres antes de la entrega, sin usar `npm audit fix --force`, que puede romper versiones.

## 9. Integración con los otros módulos

- **Catálogo (Integrante 2):** las rutas de alta, edición, baja e importación de animes deben protegerse con `authToken` y `authorize('ADMIN')`. El middleware `authorize` recibe los roles sueltos, no como arreglo. Los imports van desde `../middlewares/`.
- **Biblioteca, reseñas y estadísticas (Integrante 3):** usan `authToken` y leen `req.user.id` y `req.user.rol`, que es exactamente lo que este módulo deja en la petición. Para la ruta `/api/usuarios/me/estadisticas` no hay choque con `/:id`, porque ese patrón solo captura un segmento.
- **Variables de entorno compartidas:** los tres deben usar el mismo `JWT_SECRET`. Si difiere, un token firmado por un integrante lo rechazan los demás.
- **Orden en `app.js`:** el `errorHandler` debe registrarse después de todas las rutas, como ya está hecho.

## 10. Configuración requerida

El servidor lee un archivo `.env` en la raíz, que no se versiona. Reglas que valida `env.js` al arrancar:

| Variable | Regla |
| --- | --- |
| `MONGO_URI` (o `MONGODB_URI`) | Obligatoria |
| `JWT_SECRET` | Obligatoria, mínimo 32 caracteres y sin palabras de ejemplo |
| `JWT_EXPIRY` | Formato de duración, por ejemplo `24h` o `7d` (por defecto `24h`) |
| `PORT` | Entero entre 1 y 65535 (por defecto 3000) |

Los valores reales no se documentan acá ni se suben al repositorio.
